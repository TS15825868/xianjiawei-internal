# 仙加味｜手動發布人工查核與狀態不可冒充（2026-10-26）

## 發現的正式問題

前端原本在部分平台未確認時顯示「手動補登已發布」；現行後端 `manual_required -> published` 本就未開放，點了只會收到錯誤。另一份 `manual-publish-tools.js` 更會先將 `approved` 貼文變為幾秒後排程，再請求 `status=published`，在排程先執行或外部發文結果不明時，存在重複發文與假成功風險。

## 目前採用的零費用安全處理

- 取消所有這種直接補登按鈕、定時轉換和繞過流程；後端 `POST /api/posts/:id/status` 明確拒絕請求 `published`。
- `published` 只能由既有受控發布器在取得平台正式遠端 ID／LINE 官方請求 ID 後設立；外部 Webhook 必須同時有真實 `published` 狀態，且 D1 接收回執必須成功。
- 前端「人工發布查核資料」繼續可查看與複製貼文文案、圖片、各平台入口及官方回執。依 D1 `social_publish_deliveries.platforms` 逐平台分辨已知成功；已發表且有遠端 ID 的平台**不再列入待人工核對**。
- D1 沒有成功回執、只有 `HTTP 200` 或狀態顯示 `sending`／`manual_required` 時，資料包只列「待人工核對」，不推定未發、不可直接重試。
- Threads 連線燈號保留正式平台探測結果，不再被舊工具硬改成「已連線」。Metricool 草稿不可擅自自動發布。
- 如需人工結案，必須有可稽核之官方真實遠端發布證據及獨立安全的受權登錄流程；這輪先移除壞掉的舊捷徑，不捏造官方發送回執。

以上變更不修改舊貼文、不刪除 ERP 資料、不使用新的付費資源，也沒有任何對顧客自動發訊動作。

## 2026-10-26 舊發布回執完整性及狀態一致性

歷史 `social_publish_deliveries` 即使寫入 `status='published'`，若缺少平台核發的 `remote_id`，仍不能當作已發布證據。此類紀錄標記 `published_receipt_missing` 進人工核對，不會再次發送；晚於排程窗口的既有紀錄也採相同規則。

貼文中心把 `manual_required` 顯示為「需人工核對」，不把結果不明誤寫成「未發布」。人工查核資料包與視窗都只依 D1 的有效遠端 ID 確定成功平台；立即發布 API 只有在真正可重試的結果才提示可能重試，遇到人工核對不會暗示自動重新發送。未修改任何正式顧客訊息、舊貼文或發布紀錄。

## 全平台已驗證回執的中斷自動復原（2026-10-26）

若已核准且已排程貼文的**所有指定平台**都已有 D1 `status='published'` 與有效遠端回執 ID，但 Worker 在寫入 `social_posts.status='published'` 前中斷，舊版會在排程逾時後誤設人工核對。新版在逾時檢查中，只有全部平台均已保存遠端 ID 才能**不呼叫任何外部平台**，僅以 D1 條件式寫入補完本地狀態；使用最後一筆已存遠端接受時間作為原發布時間。寫入失敗或沒有更新到唯一狀態時回報未確認，絕不假裝已發布。

有任何平台缺遠端 ID、需人工發布（如 LINE VOOM）、仍在重試、或外部結果不明時，原本的人工查核流程保持不變。

## 2026-10-26：新貼文平台選擇不再偷偷改變

新增貼文原本預設勾選 Facebook／Instagram／Threads，但 Threads 尚未取得 Metricool 遠端發布驗證；舊版 `safePlatforms` 會默默剔除不認得的平台，而且完全沒勾時還會暗中改成 FB／IG。這容易使新貼文在審核或發布時選到不符合原意的平台。

新版保留原本 FB／IG 的新增草稿預設勾選，**Threads 必須由使用者親自勾選**；編輯舊貼文完整保存原選擇。舊插件若補上 Threads 選項，也預設不勾選。建立／編輯貼文時，後端必須取得非空、全數受支援的平台陣列；不得默默跳過混入的不支援項目、也不得將未選擇的平台偷偷改成 FB／IG。正式舊稱 `LINE OA 廣播` 會正規化為現行 `LINE OA`，避免新資料存成已廢棄的平台名稱。

使用者仍需要通過 16 項圖文人工審核與圖片正式外觀規則，任何本輪程式變更都不會直接核准或發布貼文。
